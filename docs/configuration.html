Configuration ​

Coding providers ​

Open Settings → Providers. Choose New provider, name it (for example, Claude LiteLLM), select a coding-agent adapter, and configure its connection. You can create several providers using the same adapter. Claude Code and Codex use native integrations; Pi uses its native RPC interface, OpenCode uses direct ACP, and other coding agents use acpx. Field guidance and examples live behind info icons: hover, focus or tap to read them.

Choose an enabled Default provider for new chats. Each provider has a default model; leave it blank to use the adapter's default. The chat picker selects named providers and can override the model and launch options for that conversation. An explicit choice in this browser is remembered across reloads; saving provider settings clears that browser override so the saved defaults take effect. Unsent model and option edits are retained separately for each provider while switching. Switching to another provider of the same agent keeps the conversation: ORC rebuilds the native session for the new account on the next turn and replays a bounded transcript of the chat so you can continue where you left off. Switching to a different agent starts a new conversation. Existing conversations retain their provider ID and model when the default changes. Disabling a provider hides it from new launches while allowing its existing conversations to resume. Conversations saved before profiles existed remain pinned to their original native provider.

Phone layout · Compact context action

For Claude, Codex, OpenCode and Pi, Executable path overrides the local binary for native chat, model discovery and provider terminal launches. Enter a path without arguments, or leave it blank for the default installation. Paths with spaces and ~/ work. SSH uses the remote installation. Changes apply at the next launch; ORC does not restart running processes.

Advanced configuration starts collapsed:

  • Environment overrides apply to launches and native model discovery, including SSH. Values override the execution environment; an empty value clears an inherited value. Use variables such as CODEX_HOME or CLAUDE_CONFIG_DIR for a separate CLI configuration, or set Config directory as described below. An explicit environment row wins over that directory. ORC does not create login credentials or copy an existing login into a new directory.
  • Mark sensitive values Secret. Credential names such as ANTHROPIC_AUTH_TOKEN require this automatically. Secrets are encrypted on the API host and are write-only in the UI. An untouched saved placeholder preserves its value; entering a replacement changes it. Remove a row to stop overriding that variable. Transport and ORC connection variables are managed by ORC.
  • Chat launch options (JSON) accept validated adapter options: Claude SDK options such as {"effort":"high","maxTurns":20}, or supported Codex/acpx argument arrays. ORC owns session, transport and working-folder arguments. Explicit session options take precedence over provider defaults. Native terminal launches use provider environment and, for Claude/Codex, model; chat JSON options are for the chat adapter. Package setups keep their own launch configuration.

Separate Claude and Codex accounts ​

Create another provider with the same adapter to work with more than one Claude Code or Codex login. While creating the provider, enable Use a separate account, or open an existing provider and set Config directory:

AdapterVariableDefault
Claude CodeCLAUDE_CONFIG_DIR~/.claude
CodexCODEX_HOME~/.codex

Each directory holds that account's CLI login, session history and state. The provider passes it to native chat, model discovery and terminal launches for Claude/Codex profiles; other adapters ignore the field. ~/ expands on the API host, so use an absolute path for an SSH execution host. Leave it blank to use the host default. An explicit CLAUDE_CONFIG_DIR or CODEX_HOME environment row still wins.

The provider card reads the account label, plan and organization from the CLI's own files on the API host and shows a copyable sign-in command. Run that command once in a terminal, sign in, then select the provider in the chat picker. ORC never stores, refreshes, relays or returns credentials. Two providers that point at the same login are flagged so a switch does not silently reuse one account. Use for new sessions saves that provider as the default without opening the full form.

Settings → Usage shows a quota card per configured Claude/Codex provider, and session discovery, the live-session watcher and transcript search include every configured directory. Remote SSH accounts are not inspected: identity, quotas and session discovery for separate accounts currently read the local API host only. ORC does not rotate accounts automatically when a quota is exhausted; switch the provider in the picker and continue.

Use Save changes to save the provider list, default and advanced settings together. Drafts survive switching providers and Settings sections. Use default clears an executable override; Discard changes restores saved values. Failed saves retain the draft. Concurrent edits are rejected rather than overwriting another device's settings; Discard draft and reload loads the saved version.

Pi ​

Install Pi 1.5.2 or newer on the execution host, with Node.js 22.19 or newer, and configure its model credentials in Pi. Create a provider in Settings → Providers and choose Pi. Pi is optional and is not enabled by default. ORC uses pi --mode rpc, preserving Pi's own credentials, extensions, skills and session files. An executable override selects the local Pi installation; SSH uses the remote installation.

The model picker discovers configured models without an inference turn. Use provider/model to distinguish identical model IDs from different providers. Chat launch options (JSON) accepts an object such as:

json
{
  "thinkingLevel": "high",
  "steeringMode": "one-at-a-time",
  "followUpMode": "one-at-a-time",
  "autoCompaction": true,
  "autoRetry": true
}

Thinking levels are off, minimal, low, medium, high, xhigh and max; Pi applies the selected model's limits. Queue modes are all or one-at-a-time. These controls also work as native Pi options for agent jobs using backend pi. Queue mode, auto-retry and auto-compaction changes are saved to Pi's own settings on the execution host, so external Pi sessions use them too. Thinking level is scoped to the ORC session. ORC owns transport, session identity, working folder and its permission bridge; arbitrary Pi command-line arguments are not accepted.

Pi supports streamed text/thinking and tool results, images on compatible models, native session resume, Send now steering, cooperative Stop, extension questions, permission prompts, live permission changes and /compact. Default permissions ask before each tool; Accept edits allows Pi's edit/write tools, and bypass permits all tools. An approval for the session applies to that tool name. This gates Pi's tool calls; it is not an operating-system sandbox or a restriction on extension code. Plan permissions and ORC tool whitelists are rejected rather than silently ignored.

With ORC tools enabled, ORC registers an authenticated, scoped MCP connection through a temporary session extension. It waits for tools to connect and refuses to start if the bridge fails. It does not edit ~/.pi/agent/mcp.json or .pi/mcp.json. Resume uses Pi's exact native session UUID; missing sessions produce an error instead of creating another conversation. Keep the execution host and its Pi session directory available for saved conversations.

Pi's terminal-only custom components and editor replacement are not reproduced in ORC. Native Pi sessions are discovered and can resume in chat or a terminal; see Live agent sessions for session directories and provider selection. Fork/rollback and native account quota controls are not exposed. Active ORC rules that require unavailable interception prevent the session from starting.

Storage and API ​

Authenticated GET/PUT /api/settings/providers reads and replaces {providers, default_provider_id, revision}. Each provider has id, name, agent, enabled, executable, optional home, model, optional options, and environment: [{name, value, secret}]. home is the CLI config directory used by Claude Code and Codex providers; blank or absent means the host default. Secret values are returned as null; send that placeholder unchanged to retain a saved secret with the same provider and variable name. New or renamed secrets require a value. Send the current revision when saving; stale writes return 409. An existing provider's adapter is immutable; create another provider to change adapters.

Authenticated GET /api/settings/providers/accounts returns the account identity ORC can read from each provider's config directory: status, label, organization, plan, duplicate marker and a sign-in command. It never returns tokens or credential contents.

Private configuration lives under providers.instances and providers.default_id in the server's JSON config. Encrypted values use ORC's machine key at ORC_HOME/secret.key; back up that key with the config. Provider secrets are excluded from readable workspace preferences. Existing preferences.agents, preferences.provider_paths and chat defaults are migrated when saving Providers and remain compatible with GET/PATCH /api/settings. Without saved profiles, the existing CLI login, paths and chat settings are used.

Local account limits starts collapsed. Check limits reuses the local-account quota reader below; it does not report gateway/Bedrock billing or SSH quotas. There is no provider health polling. Native Claude quota rejections and Codex usage-window notices include reset times when supplied by the agent. Claude extra usage is distinguished from a blocked request. A failed turn holds queued messages; retry explicitly after access returns. ORC does not switch accounts automatically or schedule quota retries; use the chat picker to move the open conversation to another account of the same agent.

Project workspace environment ​

Open a project and use Edit → Workspace, or fill the Workspace step while creating a project. These settings apply to terminals, flow-node sessions, chat turns and job actions that run in that project's folders.

  • Setup script runs once in each new managed worktree under .orc/worktrees, .claude/worktrees or .codex/worktrees, before the first agent or terminal starts there. ORC runs it with the project's shell on the terminal's host, from the worktree folder. A failed or timed-out script is recorded with its output and the agent still starts. The script does not rerun for an existing worktree, and a project's main checkout is never prepared for you. Setup timeout is 900 seconds by default (30–3600).
  • Dev script starts with Start dev server in the terminal launcher. It opens as a shell terminal in the current folder; the first printed http(s) URL becomes the workspace preview link. Loopback hosts such as 0.0.0.0 and :: are shown as localhost, and later URLs in the same terminal are ignored.
  • Port range gives each workspace a stable block instead of a single port. The first workspace of a project starts at 3100 with 10 ports unless Port range start or Ports per workspace is changed (1-100). Later workspaces take the next free block, and blocks never overlap on the same API host, even across projects. Ports already bound on a local host are skipped; SSH hosts cannot be probed, so only ORC's own allocations are avoided there.
  • Environment holds extra variables for every launch in the project. Mark sensitive values Secret to encrypt them with ORC's machine key; secrets are write-only and read back as empty placeholders. An untouched placeholder keeps the saved value. ORC_ names are reserved for ORC.

Workspaces export PORT, ORC_PORT, ORC_PORT_END, ORC_PORT_COUNT and ORC_PORT_1…ORC_PORT_<count>, plus ORC_PROJECT_ID and ORC_WORKSPACE (ORC_WORKTREE only inside a managed worktree). Project environment values are added last.

Setup status, ports and the preview link appear in a session's inspector and on a task's Git links, and are readable through GET /api/workspaces. The preview belongs to the workspace path and is cleared when its dev terminal exits. Deleting a project removes its workspace rows. Flow nodes run in the task's checkout; per-node worktrees are not created yet.

Manual context compaction ​

For an existing idle Claude, Codex or Pi chat, choose Compact context from session actions (an icon in the expanded desktop header), or send /compact. This uses the same native session: Claude's SDK command, Codex's thread/compact/start RPC, or Pi's compact RPC. Progress, failures and completion use the normal conversation stream and history. Running turns, attachments and integrations without native support cannot be compacted this way. Keep automatic compaction under the agent's own control; Claude sessions with slash commands explicitly disabled must enable them first. There is no ORC idle-compaction timer. Compaction summarizes model context and may use provider quota; it does not erase the displayed ORC transcript.

Usage in Settings ​

Open Settings → Usage for session token history and account quotas. History shows lifetime token totals for imported native sessions started in the last 7, 30 or 90 days, or all time, across all projects. Daily rows use UTC session start dates; they do not represent tokens consumed that day. Missing counts are reported separately, Cursor counts are estimates, and these totals are not billed costs. Claude totals include input, output, cache-creation and cache-read tokens, with repeated assistant messages counted once. Older Claude counts refresh from available transcripts on the next session sync, even for unchanged sessions. Until a refresh succeeds, those counts are excluded from token totals and reported among sessions without complete token counts. Inaccessible transcripts remain unknown; ORC does not substitute their old partial counts. The existing session importers determine which tokens are counted; this view does not rescan transcripts or include managed gateway sessions a second time.

Account quotas show percentage used and reset times for local Codex and Claude accounts on the API host, one card per configured provider. ORC reads the existing CLI login from each provider's config directory—CODEX_HOME/auth.json (default ~/.codex/auth.json) or CLAUDE_CONFIG_DIR/.credentials.json (default ~/.claude/.credentials.json)—and requests quota data from the provider over HTTPS. Credentials stay on the server and are never returned to the browser. Keychain-only, API-key and SSH-host logins are not supported. Missing logins, expired access and unsupported provider responses display an unavailable state. Sign in again using the provider CLI when access expires; ORC does not refresh or modify provider credentials.

The authenticated read-only routes GET /api/usage/history?days=30 and GET /api/usage/quotas expose the same data. History accepts 7, 30, 90, or 0 (all time). Quota requests share a 60-second server cache and an 8-second provider timeout. The Usage panel polls quotas once a minute while open; Refresh retries both views while respecting that cache. Provider quota interfaces can change; unavailable quota data does not prevent session history from loading.

Where ORC keeps its config and data, every config key and environment variable you are likely to set, logs, running as a background service, and authentication.

Notification and audit retention ​

Set these server-wide preferences in Settings → Storage or the JSON config:

Config keyDefaultAllowed days
preferences.notification_retention_days301–3650
preferences.audit_retention_days901–3650

All notifications expire, including unresolved requests' alerts. Audit history retains the notification title and message independently until the audit event expires. The audit log is also capped at 200,000 rows, oldest removed first. Expiry filters apply immediately; the API performs bounded cleanup at startup and every minute. Freed SQLite pages are reusable but the file may not shrink. See Notifications.

Precedence ​

Later wins:

  1. ~/.orc/config.json
  2. ./.orc/config.json
  3. Environment variables
  4. Global CLI flags (--port, --host, --db, --secret, --log-level, --runner-timeout, --runner-max-jobs, --snapshot-max-bytes)

An invalid config file stops ORC with Invalid orc config and the failing key.

The task loop picks up todo and changes_requested tasks and runs agents on them.

Ports ​

PortServes
7700REST API (/api/*), dashboard (/), MCP (/mcp), OpenAPI (/openapi.json), Swagger UI (/docs)

Change it with api.port, ORC_API_PORT or orc --port <n> daemon start. The desktop app reads the same setting.

Desktop automatically chooses an available loopback port if another application occupies this port and no daemon is already running. It saves the selected port and loopback host in global config after a successful start, so default CLI and stdio MCP connections follow it. Explicit overrides still win. See Desktop app for reuse and recovery behavior.

The daemon writes daemon.json next to daemon.pid once its API is listening. The record contains its PID, bound port, instance ID, version, database/config paths, start time and whether authentication is enabled, never the secret. It is written atomically with user-only file permissions and removed on clean shutdown. Desktop ignores stale records whose PID is no longer the active daemon.

Health check (no auth needed):

bash
curl -s http://127.0.0.1:7700/api/health

Logs ​

~/.orc/logs/orc.log holds JSON lines. It rotates at 10 MB and keeps three rotated files (orc.log.1 to orc.log.3). The terminal gets the same entries in readable form on stderr.

bash
grep '"level":"error"' ~/.orc/logs/orc.log | tail -20
tail -f ~/.orc/logs/orc.log | jq .
orc --log-level debug daemon start

Run as a background service ​

orc daemon start runs in the foreground. To start it at login and keep it running:

bash
orc daemon install     # register and start now
orc daemon uninstall   # remove the registration
PlatformMechanismRestarts on crash
macOSlaunchd agent ~/Library/LaunchAgents/com.orc.daemon.plistYes
Linuxsystemd user service ~/.config/systemd/user/orc-daemon.serviceYes (on failure)
WindowsRegistry Run key HKCU\Software\Microsoft\Windows\CurrentVersion\Run\OrcDaemonNo

No admin rights needed. Service output goes to ~/.orc/daemon.log on macOS and Linux.

bash
orc daemon stop                       # stop the running daemon
orc daemon status                     # list scheduled jobs and their last runs
orc status                            # API health and counts
launchctl list | grep orc             # macOS
systemctl --user status orc-daemon    # Linux

orc daemon install refuses an orc that lives under nvm, fnm, volta, asdf or nodenv paths. Install a pre-built binary, or pass --force.

orc daemon start merges your login shell's PATH on macOS and Linux, so agent CLIs such as claude, codex and cursor-agent are found when the daemon runs as a service.

If a daemon already answers on the port, the desktop app uses it instead of starting its own.

orc api starts only the API server, without the scheduler, watchers, gateway or task loop.

Authentication ​

With no secret, ORC accepts every request. Keep api.host on 127.0.0.1 in that case.

Set a secret:

bash
orc --secret "$(openssl rand -hex 32)" daemon start   # one run

or put it in ~/.orc/config.json as api.secret, or set ORC_API_SECRET. The desktop app generates and saves one for you.

ClientHow it authenticates
CLI, stdio MCP on the same machineReads the secret from config or ORC_API_SECRET
HTTP clients, HTTP MCPAuthorization: Bearer <secret or access token>
DashboardAsks for the secret once and stores a signed HttpOnly cookie for api.session_days
Desktop appSends the secret it configured

Unauthenticated paths: /health, /api/health, /api/auth/session, /api/auth/token. Handoff upload, session-sync, skill download and scratchpad content URLs skip the secret but check their own signed, expiring link.

Access tokens ​

An access token is a signed bearer credential that expires. Use one instead of the raw secret for agents and scripts.

Create one under Settings → Security, or:

bash
curl -s -X POST http://127.0.0.1:7700/api/auth/token \
  -H 'Content-Type: application/json' \
  -d '{"secret":"'"$ORC_API_SECRET"'"}'

Returns {"token": "...", "expires_at": <unix seconds>}. Pass expires_at (unix seconds) to choose the expiry, up to 365 days. Rotating the secret revokes every token.

For exposing ORC beyond localhost, see Self-hosting.

Direct ACP commands ​

agent_loop.acp_commands optionally maps agent IDs to { "command": "executable", "args": ["literal", "arguments"] }. Add the ID to preferences.agents to select it in chat. The opencode agent already ships a built-in direct ACP command (opencode acp); an acp_commands.opencode entry overrides it, for example to pin a specific installation. Commands run on the chosen execution host; authenticate using that agent's own login or existing secure environment configuration. Arguments are not shell expressions and must not contain secrets. See Connect agents for setup, capability negotiation and permission limitations. Existing chats retain their selected backend even if this configuration changes.
